## Root cause analysis of the "Este lote no está disponible" symptom

The GET `/api/candidates/batch/{batch_id}` endpoint (server.py:738) only runs `get_current_user` + a Mongo `upload_batches` lookup and raises 404 on a miss — **confirmed: no ownership check**. So, as the user reasoned: **403 ⇒ auth** (expired/invalid JWT or inactive user), **404 ⇒ the batch_id is genuinely absent from `upload_batches` in the live Atlas DB.**

Two architectural defects in the deployed code make both outcomes likely under the 2-replica topology:

**A. File bytes and the work queue are per-process (in-memory), not shared across replicas.**
`BackgroundProcessor` (background_processor.py:125-170) keeps:
```python
self.jobs: Dict[str, ProcessingJob] = {}   # "objetos vivos de ESTA réplica"
self.file_data: Dict[str, bytes] = {}      # raw CV bytes, in memory
self.queue: asyncio.Queue                  # in-process work queue
```
Only batch/job **state** is persisted to Mongo ("para visibilidad multi-réplica"). The worker does `job = self.jobs.get(job_id)` and **skips any job not in its own process memory**. With 2 replicas behind the LB, a batch POSTed to replica A has its bytes/queue only on A; replica B's workers can never process those jobs. Job state rows stay `pending` and the batch's quota lease stays live.

**B. No rehydration on (re)start → permanent orphans.**
`initialize()` (background_processor.py:142) only creates the asyncio.Queue. There is **no code that reloads `pending` `upload_jobs` from Mongo back into `self.jobs` / `self.file_data` / `self.queue`.** If the pod restarts (deploy, OOM, reschedule), all in-memory bytes are lost, the Mongo `upload_jobs` stay `pending` forever, and nothing re-enqueues them.

**C. Quota interaction → the 429.**
`create_batch` (background_processor.py:268) calls `reserve_batch` **before** inserting the batch doc. `reserve_batch` enforces `QUEUED_BATCHES_PER_USER = 2` live batches, each held for `LEASE_SECONDS = 600` (10 min). A batch released only by `finish_batch_if_done` (when no `pending`/`processing` jobs remain). Under defect A/B, jobs that never complete keep the batch "live" for the full 10-minute lease, so **up to 2 stuck batches block the 3rd upload with HTTP 429** (`"Límite de procesamiento: 2 CVs simultáneos y 2 lotes en espera por usuario"`).

**How this produces the user-facing message:**
- A batch processed on the "wrong" replica (or lost to a restart) leaves `upload_jobs` stuck `pending`; the UI keeps polling and eventually the batch is cleaned/expired or never progresses → poll returns 404 (batch doc gone/expired) → "Este lote no está disponible."
- Alternatively, if the JWT expired during the long-running batch, the poll returns 401/403 → same message (frontend maps 403/404 identically).
- Meanwhile stale/live leases push the user to 429 on new uploads.

I could **not** confirm the concrete orphaned-lease / pending-job counts because they live in the inaccessible `ATLAS_URI` DB (see headline). The mechanism is verified from source; the live data state is inferred, not observed.

## Recommended fixes

**CODE (applied by E1 in the source env, then redeploy):**
1. Make CV processing replica-safe. Either (a) persist the raw file bytes to **shared** storage (GridFS in the same Atlas DB, or R2/object storage) keyed by job_id so any replica can fetch and process, and have workers pull `pending` jobs from Mongo rather than only an in-process `asyncio.Queue`; or (b) as an interim, pin the deployment to **1 replica** so bytes and queue stay co-located with the worker. (Tier is configured for 2 replicas — a single-replica interim removes the cross-pod loss while the shared-storage fix is built.)
2. Add **startup rehydration**: on `initialize()`, load `upload_jobs` with status `pending`/`processing` for this deployment and re-enqueue them (requires the bytes to be in shared storage per #1). Without this, every restart orphans in-flight batches.
3. Harden quota release so a failed/abandoned batch releases its lease promptly (e.g. release on batch failure, shorten lease, or a sweeper), to stop stuck batches from causing spurious 429s.

**USER / OPERATIONAL:**
4. The live production data is in **your own Atlas cluster (`ATLAS_URI`, DB `atlas_talent_vault`)**, not the Emergent-managed DB. To inspect batches/workloads/jobs (item #3/#4) you must connect to that Atlas cluster directly — Emergent's DB Manager and deployer tools point at the unused `atlas-recruiting-ai-atlas_talent_vault` DB and will mislead you. Decide whether this dual-DB setup (`ATLAS_URI` overriding `MONGO_URL`) is intended; if yes, be aware Emergent DB Manager / migrations will not reflect production.
5. Verify the 403 branch: reproduce an upload in the browser with DevTools open and watch whether `GET /api/candidates/batch/{id}` returns 403/401 (token expiry — check `JWT_EXPIRATION_MINUTES`) vs 404 (missing doc). That disambiguates auth-expiry from the orphan/404 path.
