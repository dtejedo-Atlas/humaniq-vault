# RCA — Login falla en el dominio personalizado vault.humaniq.com.mx

## Resumen (causa raíz)
El login desde `https://vault.humaniq.com.mx` falla por **CORS**. El preflight `OPTIONS` del navegador llega al backend y es **rechazado con 400 (Disallowed CORS origin)** porque el origen `https://vault.humaniq.com.mx` NO está en la lista de orígenes permitidos del backend. Tu hipótesis principal es correcta.

## Evidencia (de producción, run d82b7b62-7edd-4ccf-a9d9-01402112d6c5)

### 1. El preflight CORS se rechaza (prueba directa)
Logs del backend de producción (últimas 24h):
```
OPTIONS /api/auth/login HTTP/1.1" 400 Bad Request   (×3)
OPTIONS /api/auth/google/session HTTP/1.1" 400 Bad Request
```
El `OPTIONS ... 400` es la firma de Starlette/FastAPI CORSMiddleware cuando el `Origin` del preflight no está permitido ("Disallowed CORS origin"). El navegador entonces bloquea el `POST` real y nunca ves intento de credenciales. IP de origen `34.49.150.102` = el edge/CDN que proxea las peticiones cross-origin.

En contraste, los logins que SÍ funcionan vienen por el origen permitido (emergent.host) y pasan:
```
POST /api/auth/login HTTP/1.1" 200 OK   (varios)
```

### 2. El bundle de producción apunta a emergent.host (cross-origin)
`REACT_APP_BACKEND_URL` en el pod de producción = `https://atlas-recruiting-ai.emergent.host` (verificado: matches_expected=true). Es una SYSTEM key: la plataforma la regenera en cada deploy y reescribe cualquier URL de preview a la URL de producción. El valor de preview (`...preview.emergentagent.com`) NO llega a producción.

**Consecuencia:** el frontend servido en `vault.humaniq.com.mx` hace llamadas absolutas a `https://atlas-recruiting-ai.emergent.host/api/*` → es cross-origin respecto a `vault.humaniq.com.mx` → se dispara preflight CORS con credenciales.

### 3. La lista de orígenes permitidos NO incluye vault
Metadatos de secrets (valores nunca expuestos):
- `CORS_ORIGINS` = `"*"` (matches_expected=true). Según tu `cors_config.py`, `"*"` cae a la lista de respaldo (solo emergent.host + preview).
- `HUMANIQ_CORS_ORIGINS` está **definida y NO vacía**, y **NO es igual** a `https://vault.humaniq.com.mx` (matches_expected=false). Como tu código prioriza `HUMANIQ_CORS_ORIGINS` cuando está definida, **esta es la variable autoritativa en producción**. Dado que el preflight da 400, `vault.humaniq.com.mx` definitivamente NO está dentro de su valor.

## Respuestas puntuales

**1) Valores efectivos en el pod de producción:**
- `CORS_ORIGINS` = `*` (presente) → cae a lista de respaldo.
- `HUMANIQ_CORS_ORIGINS` = definida/no vacía, pero **NO contiene `vault.humaniq.com.mx`** (probado por el 400 del preflight). Es la que manda.
- `CORS_PREVIEW_PROXY_ORIGIN` = presente, no vacía.
- `CORS_PREVIEW_PUBLIC_ORIGIN` = presente, no vacía.
- `REACT_APP_BACKEND_URL` = `https://atlas-recruiting-ai.emergent.host` (con esto se compiló el frontend de producción). **Ninguna incluye vault.humaniq.com.mx.**
- (No puedo exponer el texto literal de los secrets; solo metadatos/igualdad.)

**2) Enrutamiento de vault.humaniq.com.mx:** frontend_type = **cloudflare**. El dominio es un Cloudflare Custom Hostname (provider=cloudflare, `ssl_status=active`, verified=true, validación http). Sirve el frontend estático (R2 vía worker). PERO como el bundle usa la URL absoluta `REACT_APP_BACKEND_URL=https://atlas-recruiting-ai.emergent.host`, las llamadas `/api` del navegador **salen directo a emergent.host**, NO van same-origin por vault → por eso aplica CORS. SSL/CDN del dominio están OK. Nota: `check_domain_status` reporta "A records do not point to expected IPs"; eso es esperado para un hostname servido por Cloudflare/R2 (no apunta por A-record directo al clúster) y NO es el problema — el sitio responde.

**3) Logs del intento de login desde vault:** la petición NO llega como POST; se queda en el **preflight OPTIONS → 400 Bad Request** (tanto `/api/auth/login` como `/api/auth/google/session`). No hay 401/403/500 del login porque el navegador aborta tras el preflight. Error efectivo: CORS "Disallowed CORS origin" para `https://vault.humaniq.com.mx`.

**4) Variable de URL pública para correos:** en producción **NO existe** `PUBLIC_APP_URL` ni `FRONTEND_URL` (no están entre los secrets del run). Hoy los enlaces de invitación/reset se arman con el `origin` que manda el frontend, así que dependerán del dominio desde el que se originó la petición. Recomendación: introducir una variable explícita (p. ej. `PUBLIC_APP_URL=https://vault.humaniq.com.mx`) y usarla para construir los enlaces, en lugar de confiar en el `origin` del request.

**5) Google login (Emergent-managed):** el bloqueo inmediato es el MISMO CORS (preflight 400 en `/api/auth/google/session`). Al corregir CORS, prueba de nuevo. Si tras ello el intercambio OAuth sigue fallando por origen/redirección no autorizada del nuevo dominio, eso se gestiona del lado de Emergent (auth managed) — abre ticket de soporte indicando que `vault.humaniq.com.mx` debe autorizarse como origen/redirect del login social.

## Causa raíz (una línea)
`https://vault.humaniq.com.mx` no está en los orígenes CORS permitidos del backend (la variable efectiva es `HUMANIQ_CORS_ORIGINS`), y el frontend llama cross-origin a `https://atlas-recruiting-ai.emergent.host/api/*`, por lo que el preflight `OPTIONS` devuelve 400 y el navegador bloquea el login.

## Qué cambiar

### Opción A — inmediata, sin código (Secrets tab)
Añadir `https://vault.humaniq.com.mx` a **`HUMANIQ_CORS_ORIGINS`** (es la variable que realmente se usa). Como es la autoritativa, basta con incluir ahí todos los orígenes válidos:
`https://atlas-recruiting-ai.emergent.host,https://vault.humaniq.com.mx` (+ los de preview si los quieres conservar). Guardar en Deployment Panel → Secrets y **redeploy**.
(Tocar solo `CORS_ORIGINS` NO sirve, porque `HUMANIQ_CORS_ORIGINS` tiene prioridad y la sobrescribe.)

### Opción B — durable, en código (E1 aplica y redeploy)
En `backend/cors_config.py` incluir `https://vault.humaniq.com.mx` en la lista de respaldo / default de orígenes permitidos, para que no dependa de un secret. Idealmente leer los orígenes de una sola fuente y documentar la precedencia.

### Mejora recomendada (código)
Definir `PUBLIC_APP_URL=https://vault.humaniq.com.mx` y usarla para construir enlaces de invitación/reset, en lugar del `origin` del request.

## Hallazgo secundario (no bloquea login)
`OPENAI_API_KEY` en producción es **inválida**: el backend registra repetidamente
```
embedding_service - ERROR - Error code: 401 ... Incorrect API key provided: sk-proj-...Le0A ... invalid_api_key
```
Esto rompe la generación de embeddings / matching (no el login). Corregir `OPENAI_API_KEY` en Deployment Panel → Secrets.
